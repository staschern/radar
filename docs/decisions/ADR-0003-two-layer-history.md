# ADR-0003. Двухуровневое хранение дневной аналитики

- **Статус:** принято
- **Дата:** 2026-08-18
- **Контекст ТЗ:** Радар §10.1

## Контекст
Требование заказчика: «всю историю ежедневных аналитик в сжатом виде и удобном для
быстрого анализа в будущем хранить в файлах гита — чтобы можно было быстрее
опираться на эти данные».

Полный отчёт (16 блоков) для этого не годится: перечитывать 20 таких файлов, чтобы
восстановить картину месяца, дорого и по времени, и по контексту модели. Одной
JSON-строки с числами тоже мало: она не хранит причины, ожидания и то, что из
вчерашних сценариев сбылось.

## Решение
Два дополняющих слоя, оба пишутся в одном коммите с отчётом.

**Уровень A — `data/radar_history.jsonl`.** Машинный. Одна строка = один день,
только числа и короткие строки. Назначение: расчёт дельт «день/неделя», построение
графиков, агрегация трендов за N дней без парсинга текста. Отсутствующие данные —
`null`, никогда не выдумываются.

**Уровень B — `data/daily/YYYY-MM-DD.md`.** Человекочитаемый. Жёсткий шаблон до
~40 строк: триггер дня, три факта, ключевой риск с оценкой, три сценария с
вероятностями, **что подтвердилось из вчерашних сценариев**, что взять на карандаш.
Назначение: восстановить контекст за 20 секунд и оценить качество прошлых суждений.

## Почему не один слой
- Только JSONL → теряются причины и нарратив; невозможно понять, почему в тот день
  был выставлен `flag_portfolio_review`.
- Только markdown → каждый расчёт дельты требует парсинга прозы, что ненадёжно.
- Только полные отчёты → неподъёмный объём чтения при ретро-анализе.

Ключевой элемент уровня B — блок «что подтвердилось»: он превращает историю из
архива в инструмент калибровки, показывая, какие типы прогнозов у агента системно
сбываются, а какие нет.

## Следствия
- Дневная сводка обязана укладываться в шаблон и лимит строк, иначе слой теряет
  смысл (превращается во второй полный отчёт).
- Обе записи append-only; исправление — новой строкой с полем `corrects`.
- При ~400 строках JSONL — свёртка в `data/archive/radar_history_YYYY.jsonl`.
- Ежемесячно имеет смысл собирать `data/monthly/YYYY-MM.md` — свёртку из дневных
  сводок (решение отложено до накопления первого месяца данных).
